== How to Read This Guide

=== The Identicon

Every component in the knowledge base has a formal public identity. This guide makes
that identity visible as an *identicon*: a small square image computed
deterministically from the component's own public identifier — a visual hash of
identity, and nothing else. Its purpose is recognition: the same component draws
exactly the same identicon everywhere it appears — in this guide's HTML and PDF, in
print, and onscreen in applications such as Komet, all of which compute it from the
same identity data — so you can recognize a component at a glance, and see that two
references name the same thing, before reading a word. Because it is derived from
identity alone, an identicon carries no meaning about what the component is; the
name and the sigil carry that.

=== Koncept Badges

Every formally identified term in this guide renders as a *Koncept Badge*: a kind
sigil when the kind calls for one (next section), then the identicon, then the
component's name in small caps. A sigil always immediately precedes an identicon —
it marks what kind of thing the identicon identifies, and never stands alone in a
badge. A badge is not styling; it is a reference to one exact component in the
knowledge base, and it links to that koncept's entry in the Koncept Glossary at
the end of this book, where its definition, axioms, and identifiers live. The prose is knowledge-base-native too:
each chapter's narrative is itself stored in the knowledge base and rendered here,
so the same content backs this guide and every other surface that reads the set.

=== The Component Kinds

Everything in the knowledge base is one of a small set of component kinds, and a
badge is honest about which kind it names. The scheme is _Koncept bare, everything
else marked_: a Koncept badge carries no extra mark, and every other kind announces
itself with a sigil ahead of the identicon.

=== Pattern-Shape Tables

Each pattern's chapter renders its shape as a numbered table — for example
<<koncept-pattern-table-DescriptionPattern>> — organized as one three-row group per
*Model Feature*: first the pattern's referenced component, then each declared
field, 1-indexed, in declared order.

* An italic label row names the feature: _Referenced component_ (the component —
  concept, semantic, pattern, or STAMP — this pattern's semantics attach to) or
  _Field N_. The referenced component is never numbered "Field 0" because it is
  not part of the fields array: it is a chronicle-level property of the semantic,
  structurally separate from the field values.
* A content row names the feature's *Meaning* — the concept saying what a value of
  this feature is — its *Purpose* — the concept saying why the pattern carries
  it — and its *Data type*, drawn from the closed set of data-type concepts the
  platform actually resolves. The referenced component has no data type, so that
  cell is an em dash.
* An indented _e.g._ row shows the feature's value on one real semantic already in
  the knowledge base — deterministically the earliest-authored one, so the example
  is stable across regenerations — rendered as a badge when the value is itself an
  identified component, and as plain text otherwise. A pattern with no semantics
  yet simply has no e.g. rows.
* An indented _default_ row shows the field's value from the pattern's default
  value semantic (see the Default Values chapter), rendered the same way. Only a
  pattern with an authored default carries these rows.

== Expression Languages

A query over ANF needs a small set of operators, and those operators overlap the
logics a clinical query author already knows: Clinical Quality Language, the SNOMED
CT Expression Constraint Language, and EL++ all spell an AND, a comparison, and a
descendant-of. Whether those are this set's operators is never a matter of matching
names. Two constructs are the same construct, or one is definable from the other, or
one agrees with the other on everything it covers and covers more, or they are
unrelated. Each of those is a claim of the kind a proof can settle. The set records
the claim as data, and the build runs the check.

=== One AND, Three Places

There is one idea of AND and three places it is used. AND means every operand is
required, not just some of them, so the result is only what is all of the operands at
once, and adding an operand can only narrow the result, never widen it.
k:GenericAND[] holds the idea and no keyword. Beneath it by is-a sit k:ELAND[] on
classes, which is the inherited And concept keeping its identity, k:SetAND[] on sets,
of concepts, statements, or subjects alike, and k:PresenceAND[] on presence values.
Every keyword binds to an instance, never to the parent, because two things are the
same construct only when they work on the same kind of thing. A set is one kind of
thing whatever its members are, which is why the set operations are one construct
each: ECL's `AND` on concept sets and CQL's `intersect` on lists of statements name
k:SetAND[] in two spellings. k:GenericOR[] has the same shape with two instances,
k:SetOR[] and k:PresenceOR[]. OR means any one operand is enough, so adding an operand
can only widen the result. It is the inherited Or concept itself, because EL++ has no
OR and there is no class instance to keep beneath it. NOT gets no generic, and that is
the check that the shape is right: EL++ has none, sets have k:SetDifference[], which
takes the first operand and leaves out whatever is also the second and has no generic
because nothing else subtracts, and k:PresenceNOT[] swaps a presence value, which is a
different thing.

The names follow one rule. A fully qualified name is the layer qualifier plus the
shared word, and the US English preferred name is that qualified name, so no view
ever shows three things called AND. Each logic is a dialect of English, k:CQLDialect[],
k:ECLDialect[], and k:ELDialect[], and in its own dialect the construct a logic names
reads as the bare keyword, spelled as the logic spells it, while everything the logic
does not name falls back to the qualified name. The two inherited node kinds that
were filed beside the connectives, the definition root and the concept reference, now
sit under k:LogicalExpressionVertex[].

=== Which Operators a Logic Allows

koncept-narrative::ExpressionLanguageKeywordPattern[]

koncept-pattern-table::ExpressionLanguageKeywordPattern[]

The three logics the set integrates, k:ClinicalQualityLanguage[],
k:SNOMEDCTExpressionConstraintLanguage[], and k:EL[], are members of
k:ExpressionLanguage[], and each one's allowed constructs are exactly the bindings
that name it. ECL's `<`, `<<`, `>`, `>>`, `AND`, `OR`, `MINUS`, `^`, and `:` name the
concept-set operators of the topic layer; its `{ }`, `[ ]`, `.`, and `+HISTORY` name
k:AttributeGroupRefinement[], k:AttributeCountRefinement[],
k:AttributeValueProjection[], and k:ConceptSetHistoryExtension[]; its `{{ M }}` and
`^ [ ]` name k:MemberFieldConstraint[] and k:MemberFieldProjection[]; and its `<`, `<=`,
`>`, `>=`, and `=` before a number name the comparisons, so that `<` and `>` are one
keyword on two kinds, a concept and a value. CQL's keywords bind in six roles. Its
operators name the presence connectives, the comparisons, the measure relations, the
measure operators, and the statement operators, and its function names, Count, Sum,
Min, Max, Avg, and Median, name the measure aggregates. Its unit keywords,
`millisecond` through `years`, name the eight members of k:UnitOfTime[], the singular
and the plural on one concept. Its declaration keywords `valueset`, `code`, and
`concept` name k:MemberOfReferenceSet[] and k:ConceptKind[], recording what a declared
thing is in this model. Its type keywords name the kinds its types are represented
as: `Boolean` as k:PresenceMeasureKind[], `Quantity`, `Interval`, and the numeric and
date types as k:MeasureKind[], `Code` and `Concept` as k:ConceptKind[]. Its literals
`true`, `false`, and `null` name k:PresentLiteral[], k:AbsentLiteral[], and
k:IndeterminateLiteral[]. EL++ has no surface syntax; its one keyword, AND on
k:ELAND[], is the set's own rendering. One declaration produces both the binding and
the dialect-scoped name, so the k:CQLDialectPattern[] and its siblings never drift
from the bindings.

ECL's remainder was settled in one pass. A group refinement keeps the members with one
attribute group carrying all the given attributes, a lung finding site and a tumour
morphology together, and is definable from k:ExistentialRestriction[]. A count
refinement keeps the members whose definition has a given number of attributes of a
type, none at all being how ECL asks for concepts without a laterality; it counts
attributes under the view, which EL++ cannot express, so it is distinct. A value
projection yields the values of an attribute across a set, the finding sites of
fractures, a step along an attribute at the topic layer. A history extension adds the
inactive concepts whose historical associations reach a member, because a statement
keeps the concept it was coded with and a set under today's view alone would miss it;
ECL's three profiles bind as spellings with the profile fixed. Unbound with reasons:
`<!`, `<<!`, `>!`, `>>!`, `!!<`, and `!!>`, because one level of the hierarchy is
authoring structure and a criterion built on it changes when a concept is inserted
between two others; `*`, which is Descendant or self of the root; `=` and `!=` inside a
refinement, the refinement's own spelling and Presence NOT of Equal to; `R`, the value
projection with Set AND; `{{ C active }}`, `{{ C moduleId }}`, and `{{ C effectiveTime
}}`, because the view coordinate is where a query fixes status, module, and time;
`{{ term = }}` and the other description filters, a search rather than a criterion;
and `true`, `false`, and `#`, spellings of concrete values. The member fields came
last: a reference set's members can carry fields beyond the concept they name, the
reference set that pairs SNOMED concepts with ICD-10 codes carrying the code on each
member. A member field constraint yields the concepts of the members whose named field
holds a value in a given concept set, the field being allowed to be the member itself,
which is how an ICD-10 code list becomes a SNOMED concept set; a member field
projection yields the values of a field across the active members as a concept set,
which with the constraint first runs the other way. A code is a concept in the
knowledge layer, not text, and a field that holds numbers or text has no query kind
here, so projecting it is refused. Neither is the value-set field constraint of the
Field Constraints chapter, which is authoring-time content on a pattern saying which
values a field may hold; these two are query-time reads of a reference set's members,
as k:CircumstanceConstraint[] is of a statement's fields.

=== The Middle as a Value

koncept-narrative::LiteralDenotationPattern[]

koncept-pattern-table::LiteralDenotationPattern[]

Every criterion a query puts to a statement yields a presence value: Present when the
determination found the topic present, Absent when it found the topic absent, and
Indeterminate when it could not tell. k:IndeterminateResult[] is the general idea, a
determination performed that could not arrive at a value within its frame of
reference, and k:IndeterminateLiteral[] is its presence form. Testing stored bounds exactly is always decisive. A comparison such as
k:GreaterThan[] or a relation such as k:MeasureWithin[] is Indeterminate when the
threshold or date it compares against is inside the recorded range. An HbA1c recorded
between 8.5 and 9.5, asked whether it is above 9, is neither known above nor known
below, and the query reports that rather than guessing. Criteria combine by k:PresenceAND[],
k:PresenceOR[], and k:PresenceNOT[], with k:PresenceImplication[] and
k:PresenceExclusiveOR[] definable from them. A k:Criterion[] is a test applied to one
statement: a k:TopicConstraint[] or a k:CircumstanceConstraint[] tests a concept for
membership in a concept set and is met or not met outright; a k:MeasureComparison[]
compares a measure with an interval on a measure semantic and can come out Indeterminate; an
k:AssociationConstraint[] follows the statement's associations, a step in a graph
query, and applies criteria to the statements it reaches; a k:CorrelationConstraint[]
tests a statement against a set of other statements of the same subject, an encounter
against the conditions whose onset was within its period, computing the link the
record does not hold. A comparison on the presence
measure semantic tests bounds exactly and is always decisive, so it is how a query says which
outcomes count, for a stored presence value and for the outcome of another comparison
alike: Present and Indeterminate together is everyone not ruled out, a trial's
candidate list; Absent and Indeterminate is everyone not confirmed; Indeterminate
alone is the retest list. k:StatementFilter[] takes a set of statements and returns
those that meet its criteria, and a bare comparison that could come out Indeterminate
is not accepted as a criterion, because its middle would be dropped without anyone
saying so. CQL's `where` is that filter with the presence comparison fixed to Present
and never written down, and the binding records it as data. No association is not a value but no
record, found by k:SetDifference[], never by NOT. k:Existence[] is Presence
OR across a statement set and
returns nothing on an empty set, since a presence value is a finding and an empty set
holds none. CQL's `exists` returns false there, so it is its own construct,
k:ClosedWorldExistence[], Existence read as if the store held the whole world, a
conservative extension whose one added rule is that no record counts as absent. The set operators act on groups already
sorted, which is what CQL's `intersect`, `union`, and `except` do on lists.

A performance carries one k:ResultMeasure[], which is the assertion, and its
cross-cutting measurements, k:TimingMeasure[], k:StatementTimeMeasure[], and
k:NormalRangeMeasure[], which measure other dimensions of the statement and are what
a criterion names. A request carries one k:RequestedResultMeasure[] with its own
cross-cutting k:RequestTimingMeasure[] and k:RepetitionMeasure[], whose five members
say from when, for how long, how far apart, how long each time, and how often. Any of
these can be recorded as a range rather than a point, so a comparison against any of
them can be Indeterminate. The normal range is instance data, tied to this laboratory's
method, this instrument, and this time of day, and "result within its own normal
range" can be decided only with the statement's own range. A second result is a
second statement; a cross-cutting measurement is not a second result.

What is null elsewhere does not all become Indeterminate. A determination that was
made and did not resolve is Indeterminate. A result not sought, or sought and not
obtained, has no result at all: the disposition of the act on the circumstance records
what became of it, k:CircumstanceConstraint[] asks for it, and the reason, a refusal, a
failed instrument, a decision not to perform, is an associated statement of its own.
k:SetDifference[] on a population finds the subjects with no record here, which is all that absence
of a statement can mean.

=== Conditionals

An if-then-else needs a yes or a no, and in this model a comparison can also come out
Indeterminate, so a k:Conditional[] has to be told what happens then. Each of its
conditions is a comparison on the presence semantic that names which outcomes take its
branch, Present alone or Present and Indeterminate together, and is therefore always
decided; a bare comparison that could come out Indeterminate is not accepted, for the
reason a filter does not accept one. An author who wants the middle in a branch of its
own adds a condition for Indeterminate alone and gives that branch what fits: for
measures, the widest range the two branches allow; for concepts, both, as candidates.
CQL's `if` and `case` are this with Present fixed as the outcome that takes the branch
and never written down, so an Indeterminate condition goes to the `else` branch, and
the binding records that as data; `then`, `else`, and `when` are connectors and stay
unbound. `is null`, `is true`, and `is false` are k:EqualTo[] on the presence semantic
against the three literals, which tests bounds exactly and is always decided, and bind
as its spellings. `Coalesce` is the conditional with an is-null condition, `IsNull`,
`IsTrue`, and `IsFalse` are function forms of the same tests, and `is` as a type test has
no counterpart because kinds are fixed before a query runs; none is bound.

=== Correlation

CQL relates two sources with `with ... such that`, encounters that have a condition
whose onset was during the stay, and that is a k:StatementFilter[] with a
k:CorrelationConstraint[] fixed to Present and never written down; `with` binds to the
criterion and `such that` is a connector. CQL's `without` keeps the encounters with no
such condition, and a null condition is not a match there, so it keeps the same
statements as k:SetDifference[], the first set less those whose correlation comes out
Present; `without` binds as its spelling. The general `from` query with several
sources, `return`, `all`, `let`, `aggregate`, `starting`, `sort`, `by`, and the sort
modifiers stay unbound: a join of several sources yields pairs, and no kind holds one;
`return` and `all` shape a result into a new structure, where results here are sets of
statements, subjects, or measures shaped by the projections; `let` is a name for an
intermediate value, a matter of writing; a general fold is a program, and the folds
analysis needs are the six aggregates; and sets here are unordered, with least and
greatest selection in place of sorting and taking the first.

=== Arithmetic on Measures

A k:MeasureOperator[] produces a measure from one or more measures. A measure is a
range, so the operator works on the whole range, never on one number picked from
inside it, and it never guesses how likely any value inside the range is.
k:MeasureAddition[] adds the lower bounds together and the upper bounds together.
k:MeasureSubtraction[] gives the smallest and the largest difference the two ranges
allow, so an HbA1c recorded between 8.5 and 9.5, less a threshold of 9, is minus 0.5
to plus 0.5, and a query can say at most half a point above and possibly not above at
all, which is all the record supports. k:MeasureMultiplication[] and
k:MeasureDivision[] take the smallest and the largest product or quotient that one
bound of each operand can make, and dividing by a range that includes zero is
Indeterminate. The measure semantic of the result is a concept the knowledge layer defines for
that operation: millimoles per liter less millimoles per liter is millimoles per
liter, one date less another is a length of time, milligrams per deciliter times
deciliters is milligrams, and where no concept defines the combination the operation
is refused. Presence has no arithmetic, because its measure semantic defines none.
k:MeasureConversion[] converts a measure from one unit to another, a weight in grams
given in kilograms, a glucose in milligrams per decilitre given in millimoles per
litre, by a rule between the two units the knowledge layer defines; a fixed factor
and offset scale the bounds and the resolution exactly, a rule with a width of its
own, the HbA1c master equation, widens the result by that width, and no rule refuses
the conversion. The result is a value inside the query, nothing is written, and the
statement's recorded measure is unchanged. CQL's `convert ... to` names it; `as` and
`cast` change a value's type, and kinds here are fixed before a query runs, and the
To-functions change a representation, which the transformation into ANF does before
any query, so none of those is bound.
k:MeasureLowerBound[], k:MeasureUpperBound[], and k:MeasureWidth[] give the lowest
value inside a measure, the highest, and how wide it is, the last being how a query
asks how uncertain a result is. CQL's `+`, `-`, `*`, and `/` name the four
operations, its `start of`, `end of`, and `width of` name the three accessors, and
its `duration in days between` two dates is subtraction read in whole days, as
`duration in days of` an interval is width read in whole days. CQL's `div`, `mod`,
`maximum`, `minimum`, `predecessor`, and `successor` are not bound: `div` and `mod`
re-express a value in whole units and the remainder, which is a unit's business and
not an operation on a range, since the remainder of a range is not a range;
`maximum` and `minimum` are the largest and smallest values a data type can hold,
where ANF's counterpart is the frame of reference of the measure semantic; and
`predecessor` and `successor` step a value by one unit of resolution to close an open
interval end, which ANF never needs because it records whether each end is included.

A k:MeasureAggregate[] produces one measure from a k:MeasureListKind[] list, the
measures of a set of statements gathered by k:MeasureProjection[], one entry per
statement that carries the named measure, all on one measure semantic. k:MeasureCount[],
k:MeasureSum[], k:MeasureLeast[], k:MeasureGreatest[], k:MeasureMean[], and
k:MeasureMedian[] are exact on ranges for one reason: none of them can go down when a
member goes up, so the aggregate of the low ends and the aggregate of the high ends
are the ends of the true range. HbA1c results of 7.0 to 8.0 and exactly 7.5 have a
least result between 7.0 and 7.5 and a greatest between 7.5 and 8.0, and a total
daily dose with one dose Indeterminate is at least the sum of the known doses. Every
member counts unless the aggregate is set to count only members with a value, the way
a filter's criteria say which outcomes count; CQL's `Count`, `Sum`, `Min`, `Max`,
`Avg`, and `Median` skip null, so each binds with that choice fixed and never written
down, as `where` binds with Present fixed. Which statement holds the least or the
greatest value is a selection, k:LeastSelection[] and k:GreatestSelection[], and with
overlapping ranges it returns a candidate list, the same treatment presence gives a
comparison it cannot decide. CQL's `StdDev`, `Variance`, and their population forms
are not bound, because the spread of a set of ranges has no exact range that can be
found without trying every combination of ends; `Mode`, because the most common value
of a set of ranges is not a range; `Product` and `GeometricMean`, because
multiplication across a list is exact only when nothing is negative and no ANF use
needs it. `AllTrue` and `AnyTrue` are settled the way `exists` was: k:MeasureAllPresent[]
and k:MeasureAnyPresent[] are Presence AND and Presence OR across a list of presence
values, the outcomes of one determination across many statements, and come out with
nothing on an empty list; k:ClosedWorldAllPresent[] and k:ClosedWorldAnyPresent[] read
them as if the store held the whole world, Present and Absent on the empty list, and
CQL's two functions name those with the members fixed to those with a value, which is
how CQL skips null.

=== Timing Relations

A range means one of two things. A measure whose measure semantic is a period on the calendar,
a hospital stay, has bounds where it began and ended. A measure whose measure semantic is an
instant on the calendar, an onset, or any quantity, has bounds where the value could
be. Every relation on measures is decided the same way: Present when the answer is yes
for every value the ranges allow, Absent when it is no for every one, and Indeterminate
when it is yes for some and no for others. So k:MeasureWithin[] is Absent for a stay
that ran past the end of a period, and Indeterminate for an onset recorded as March
2024 against a period that ends in the middle of March. k:MeasureBefore[] and
k:MeasureAfter[] decide the same way as k:LessThan[] and k:GreaterThan[] on every pair
of measures, and the set asserts the two equivalences. CQL's `on or before` and
`before or on` name Less than or equal to, `on or after` and `after or on` name Greater
than or equal to, and `in` names Measure within as well as concept set membership, one
keyword on two kinds. Offsets are arithmetic: `30 days or more after` a discharge is
Greater than or equal to against the discharge plus 30 days, `3 days or less before` a
surgery is Measure within against the range from the surgery less 3 days to the
surgery, and `within 7 days of` an admission is Measure within against the admission
widened by 7 days each way. k:MeasureWholeUnit[] gives the whole unit of a named size
that a measure occupies, the day of a timestamp from midnight to midnight, and every
precision-based comparison uses it: `same day as` is Equal to on the whole days,
`before day of` is Measure before on them, `difference in days between` is Measure
subtraction of the whole days' starts, and `date from` is the whole day. The units are
the calendar's own, defined in the knowledge layer, not equal buckets counted from
zero. CQL's `starts`, `ends`, and `meets` in Allen's sense are not bound, because two
ends coinciding exactly is not something a record supports, and at a resolution they
are the accessors with Equal to on whole units; `occurs` is a filler word; `properly`
is within and not equal; `point from` is unnecessary because a single value is already
a measure; `per` belongs with `expand` and `collapse` over measure lists; and `same` on
its own has no meaning, its phrase `same as` being bound.

Time has lengths and positions. A length is a duration, and its measure semantic is a
k:UnitOfTime[]: k:Millisecond[], k:Second[], k:Minute[], and k:Hour[] are fixed
lengths, while k:Day[], k:Week[], k:Month[], and k:Year[] are units of the
k:GregorianCalendar[], whose length in hours varies. One unit concept serves three
uses: the unit a duration is read in, the size Measure whole unit takes, and the
resolution of a timing. A position needs a scale with an origin, a k:TimeScale[]:
k:UnixEpochMilliseconds[], what a database timestamp and Java's Instant record,
k:UnixEpochSeconds[], the same timeline read a thousand times coarser, and
k:GregorianCalendarDate[], a civil date with no zone, counted in days from the epoch,
what Java's LocalDate records. The calendar, given a time zone, places a civil date on
the epoch scale as its whole day. A timing's measure semantic is a k:TimeReading[] on a scale,
k:Instant[] or k:Period[], a concept the knowledge layer defines the way a unit with a
measurement basis is defined; the set holds the readings, the scales, and the zones,
not the combinations. A k:TimeZone[] is a region's rule for reading the clock, the
offset from UTC at any instant with its seasonal changes, what Java's ZoneId records,
and a k:UTCOffset[] is a zone whose offset never changes, what a timestamp is written
with. A timing on an epoch scale is the same instant everywhere, so a zone changes
nothing about the instant and everything about the clock: a draw at 23:30 UTC is a
night draw in London and an early-morning one in Paris. When a record carries the
zone it was written in, that zone is the third part of the timing's measure semantic; without
one, a query reads the calendar in the zone it names, and Measure whole unit and the
calendar take the timing's own zone when it has one and the query's otherwise. CQL's
`time from`, the time of day, is the timestamp less the start of its whole day, a
composition, and `timezoneoffset from` reads the zone part of the measure semantic, which is
not an operation on the measure; neither is bound.

=== Days Covered

Of the days in a measurement period, how many did the patient have medication for.
Each dispense covers the period from its date to its date plus its days supply, which
is Measure addition and then a span. A period is built from two instants, and ANF's
period has two bounds and cannot hold an end that is itself a range, so there are two
spans: k:MeasureOuterSpan[] runs from the earliest the first measure could be to the
latest the second could be, everything that might have been covered, and
k:MeasureInnerSpan[] from the latest the first could be to the earliest the second
could be, what was certainly covered, and nothing when those cross. For single values
the two coincide, which is CQL's Interval constructor. A k:MeasureListOperator[]
produces a list of measures from a list: k:MeasureListMerge[], CQL's `collapse`,
returns the fewest periods that cover the same time, two that overlap or touch
becoming one; k:MeasureListSplit[], CQL's `expand ... per day`, returns one whole unit
for each unit any period touches, Measure whole unit applied throughout, with `per`
naming the unit and staying unbound. The days covered are the split of the merged
spans, their number is k:MeasureCount[], the measurement period split per day and
counted is the denominator, and k:MeasureDivision[] gives the proportion. A dispense
date known only to a month makes the proportion a range: count over inner spans for at
least, over outer spans for at most, and no guess in between. CQL's `distinct` is the
merge applied to single values, `flatten` needs a list of lists, which no kind holds,
and `singleton from` takes the one member of a one-member list, which least or greatest
already does; none is bound.

=== Declarations

A CQL library opens with declarations: what it is called, which data model it reads,
which value sets and codes it uses, which inputs it takes at run time, and named pieces
of logic. None is an operator, and in IKE most of the answers are the knowledge layer
and the view. A `valueset` names a value set by its identifier, and a value set is a
reference set under the view, which k:MemberOfReferenceSet[] yields; a `code` names one
concept by its code in one code system, and a `concept` names one concept by several
equivalent codes, which in IKE is one concept with identifiers in several code systems;
so those three bind under k:DeclarationKeyword[]. `codesystem` and `codesystems` are
not bound, because a code system is an identifier scheme and the concept is the same
whichever code names it, and `display` is not, because a display is a description
chosen by the language coordinate. `context` is the difference between one subject and
a population: a query over ANF runs over all statements and k:SubjectProjection[]
answers with subjects, so it is population-wide unless narrowed, CQL's `context
Patient` is the same query run one subject at a time, and its `Unfiltered` is the
default here. `parameter` and `default` are inputs, not constructs: the measurement
period is a period measure the environment supplies when the query runs, a named
literal, and a default is the value used when none is supplied. The library structure
is the knowledge layer's: `define` names an expression, and a named expression is a
concept whose definition is the expression, versioned and scoped by STAMP and
referenced from other modules the way any concept is; `function` and `fluent` are
definitions with arguments; `library`, `version`, `include`, `called`, `private`, and
`public` are how CQL packages and scopes definitions, which module and path do here;
and `using FHIR` is unnecessary because the query is over ANF, which the transformation
from FHIR produces. Where CQL's library structure meets IKE's definitions is the
clause plugin work, in which a Complex Concept Clause's vertex meanings are these
constructs.

=== Data Types

ELMfootnote:[HL7's ELM, the Expression Logical Model of the Clinical Quality Language
specification, and not Elm, the programming language for browser user interfaces.] has
twenty-three built-in kinds of value, its System types, and every literal and every type
name in a CQL library points at one of them or at a type of the data model. Each of the
twenty-three is a concept of the ELM node catalog, and each relates to the concept of the
query model for the same idea by a checked relation, the way the operators do.

The numbers, Integer, Long, and Decimal, are measures on k:DimensionlessNumber[], a
measure semantic for a number that carries no unit: both bounds the value, resolution one
for the whole numbers and the written decimal place for a decimal. The 32-bit and 64-bit
ranges are machine limits, not meaning. Boolean is k:PresenceMeasureKind[] by logical
equivalence: true is Present, false is Absent, null is Indeterminate, the three-row table
the connectives already run. String is the string data type, one idea admitted twice.

Date, DateTime, and Time are measures read as instants with the written precision as
their resolution: a Date on k:GregorianCalendarDate[], a DateTime on the epoch scale in
the zone its offset gives, a Time on k:TimeOfDay[], a position within a day counted from
midnight with no date and no zone. A Quantity is a measure on the unit its code names, one
of the units of time for a calendar word and UCUM's unit for a code; the units are the next
section's. A Ratio is a k:MeasureRatio[],
a numerator measure and a denominator measure kept as written, so 1:128 stays 1:128.

Code and Concept are k:ConceptKind[] by logical equivalence, given the code system is in
the graph: a Code is the concept carrying that code, a Concept the concept its codes
share, and the display text travels with the value without being part of the meaning.
Vocabulary, ValueSet, and CodeSystem are k:ConceptSetKind[]: the set of concepts a named
collection denotes under a view. Interval and its six typed forms are k:MeasureKind[]
itself: bounds and inclusivities the interval's, the frame from the point type, and the
resolution unstated; an interval of dates or times is read as a period. Any is
k:OperandKind[], the top of one family being the top of the other.

Every relation but three is a definitional extension: the ELM type can be defined from
what the query model already says. Boolean, Code, Concept, and Any are logical
equivalences. String and Ratio are identities, a relation kind the pass adds for types,
where an operator of another language would instead be admitted as the construct itself.
When a library is imported, a type name that is a System type is stored as the catalog's
concept for it, so the tree holds a concept the relation makes ours; a type of the data
model stays text until the model information gives those types concepts.

=== Units

A quantity is a measure on a unit, and the units come from the Unified Code for Units of
Measure, UCUM, the vocabulary CQL uses for them. UCUM's license allows its file to be
copied and used unmodified and forbids changing or deriving from its content, so the
starter set carries the file as its publisher issues it, with the notices the license
asks for, and reads it when a knowledge base is assembled rather than generating a section
from it. What the ledger holds is only what is IKE's: the parents k:UCUMProperty[],
k:UCUMPrefix[], and k:UCUMComposedUnit[] under k:UnifiedCodeForUnitsOfMeasure[], the
k:UCUMUnitPattern[] and k:UCUMPrefixPattern[] that record what UCUM says of a unit or a
prefix verbatim, the k:UCUMComposedUnitPattern[] for units built by the grammar, and the
k:UCUMDialect[] in which a unit's name and print symbol are read.

The import makes a concept for each of the seven base units and the three hundred and
five defined units, each under the property it measures, length or mass or pressure, so
that the hundred and one properties are concepts too and a unit's place says what it measures; a
concept for each of the twenty-four prefixes; and, for every unit, its code, its
case-insensitive code, its print symbol, its class, whether it is metric, special, or
arbitrary, and its definition as UCUM writes it. The names and print symbols are
descriptions read in the UCUM dialect, so a unit is found by either. Beside UCUM's fields
sit two of IKE's, marked as IKE's: the k:UnitDimension[], how much length, time, mass,
angle, temperature, charge, and luminous intensity the unit carries, and the
k:UnitMagnitude[] in the base units, both computed by following UCUM's definitions down
to the base units. Two units convert when their dimensions agree, by the ratio of their
magnitudes: an hour is 3600 seconds, a liter a thousandth of a cubic meter, a millimeter
of mercury 133.322 pascals. The twenty-one special units, degrees Celsius and the
logarithmic scales among them, are defined by functions and take no part in conversion by
ratio; the forty-one arbitrary units, international units among them, never convert, as
UCUM says.

A unit code is more than an atom: a prefix on a metric unit, a power, a product, a
quotient, a number, an annotation in braces that means nothing to the algebra. No family
can list the combinations, so a composed unit is made when it is first met, a concept
under k:UCUMComposedUnit[] identified by its canonical code, the factors in one fixed
order, so that mg/dL and mg.dL-1 are one concept while each library keeps the spelling it
used. A code the grammar cannot read is refused with its place, the way an unresolvable
name is.

CQL writes durations two ways, and the two are kept apart. A calendar word, days or
months or years, singular or plural, is one of the eight units of time, k:Day[] and its
kin, whose length depends on where it falls on the calendar. A UCUM code, d or mo or a,
is UCUM's unit of fixed length. Where the two agree they are related by k:Identity[]:
k:Second[], k:Minute[], and k:Hour[] to UCUM's s, min, and h, and k:Millisecond[] to the
composed ms. Where they do not, the definitions of k:Day[], k:Week[], k:Month[], and
k:Year[] say which UCUM unit each is not. When a library is imported, a quantity's unit
becomes a reference from the definition to the unit's concept, calendar or UCUM, with the
spelling as written kept on it, so the Quantity relation of the data type pass holds
without a waiting clause: a quantity is a measure on the unit its code names, and that
unit is a concept.

=== Data Models

A library names the types of the model it was written against: a retrieve of Condition,
a cast to Encounter, a value of Quantity. The translator describes each model in a model
information file, and those files enter the starter set the way UCUM did, unmodified,
with their notice, read by an importer when a knowledge base is assembled. Six ship:
System, whose sixteen types the ELM node catalog already holds, QDM 5.6, QUICK, FHIR
4.0.1, QI-Core 4.1.1, and US Core 3.1.1. The ledger holds only what is IKE's: the
k:DataModel[] parent, the records for a model, a class, an element, a context, a
relationship, a conversion, and a required model, the mark that writes a pattern of
IKE's own into model information, and the five dialects in which each model's names and
labels are read.

A class becomes a concept under its base class, so a model's own hierarchy is the
taxonomy, and a class with no base, or whose base is a System type, hangs under the
concept for its model at its version, since nothing hangs under the catalog's types.
Its name and its label are descriptions read in the model's dialect, "Encounter,
Performed" beside EncounterPerformed, since a QDM author writes the label. Its record
carries every field the file gives, verbatim, and beside them what IKE resolved: the
base as a concept, the code path as the element it names, the model it belongs to, the
purpose of each field saying whose it is. An element is not a concept but a semantic
about its class, the way a position is a semantic about its node kind, with the file's
fields verbatim, the class its type names when it names exactly one, and its full type
as a tree of the catalog's type specifiers, named, list, interval, and choice, so that
one checker holds a library's types and a model's element types alike.

Every identity is derived, a model from its name and version, a class from its model and
its qualified name, an element from its class and its name, so importing a file twice
writes nothing and a corrected file appends versions. The System model makes no
concept: its types are the catalog's, and the import checks that the file's members
agree with the catalog's positions, name and type. A required model absent from the
store stops the import, as does a class the file does not declare, or a model the file
neither requires nor targets.

When a library is imported, every type name is resolved before anything is written. Its
url finds the library's using declaration; the name and version there find the model,
and a declaration without a version finds the model only when the store holds one
version of it; the class name finds the class, whose concept lands in the tree where the
name was written, as a System type's did already. A retrieve's code and date paths
resolve to the elements they name, as references from the definition, walked element by
element when dotted and each step names one class; a path that walks through a
reference, as QUICK's medication.code does, stays text. A property access keeps its path
as text too, and both are counted, the worklist for the evaluation step, which will
infer the class of a source because it must. An unknown model, class, or element stops the import with its place.

The generator runs the other way. Any family of the ledger's patterns marked with the
k:ModelClassMarkPattern[] writes as model information: each pattern a class whose
identifier is the pattern's identity, each field an element typed from the field's data
type, the mark saying whether the class is retrievable and which field carries its code.
The file validates against the model information schema and imports back to its
patterns, so a library can be written against IKE's own knowledge once ANF's pattern is
settled and marked.

=== Evaluation

A library held as trees is knowledge about a question, and evaluation asks it. The
definitions run for a subject, or for every subject, against the statements a source
answers under a view, and each yields a value of IKE's own kinds or a refusal that names
its place. The evaluator is IKE's own, over the stored trees: each node kind is read into
the operands of the construct its checked relation names, and the relations are the
dispatch table, read from the store at load. A node whose kind has no relation is refused,
naming the definition, the position walked to it, and the kind, never silently evaluated.
Seventy-nine kinds are admitted in ten families, the literals, the references, the
logical and nullological kinds, the comparisons, the intervals, the arithmetic, the
aggregates, the queries, and the clinical kinds; the families the corpus needs.

Every value carries its kind, and a missing value is a value of its kind with no content:
Indeterminate presence, a measure with no bounds, a missing list rather than an empty one.
A measure is two bounds on a measure semantic, and one flag says whether it is an extent. A
value written to a resolution, an instant written to a day, spans what it could be, an
uncertainty; CQL's interval is an extent, every point of which is meant. An uncertainty
overlapping another without agreeing is Indeterminate, which is what CQL calls null for
instants of differing precision; two overlapping extents are decided. The calendar words
are IKE's units of time, weeks and finer definite spans of seconds commensurable with
UCUM's, months and years calendar spans counted in months, so adding a month to the last
of January lands on the last of February.

The evaluator reads statements through one seam, the query model's own reading of a
statement: subject, topic, circumstance kind, disposition, timing, result, statement
time, associated statements. A source answers a subject's statements, or every statement.
A retrievable class stands for a criterion, recorded on the class by the
k:ModelClassBridgePattern[]: the circumstance kind a statement must hold, the disposition
where the class fixes one, and the relation kind the bridge claims; the topic constraint
takes the retrieve's codes through the class's code path. An element's reading, recorded
by the k:ModelElementReadingPattern[], says which statement reading the element answers:
topic, circumstance kind, disposition, timing, its start or its end, result, statement
time, or the subject's birth date. Both are authored beside the model files and written
at import, the corpus's classes first, each bridge a conservative extension since every
class carries more than a statement says. A retrieve of the patient class yields the
context's subject; a retrieve of an unbridged class, a path without a reading, and a
context other than Patient or Unfiltered are refused with their place.

named; recorded, a value that differs from the expected, a reading admitted as

k:MeasureAddition[].
k:DescendantFieldConstraint[] and k:KindOfFieldConstraint[] are logically equivalent
to k:DescendantOf[] and k:DescendantOrSelfOf[]: the same concept sets, which the set
contained without saying so until now. k:MeasureBefore[] and k:MeasureAfter[] are
logically equivalent to k:LessThan[] and k:GreaterThan[]: they decide the same way on
every pair of measures, and the finite check tries every ordering of the four ends with
every combination of included and excluded ends. k:ClosedWorldExistence[], the
construct CQL's `exists` names, conservatively extends k:Existence[]: it agrees
wherever Existence has an answer and adds Absent for the empty set, the closed-world
default made into data rather than a caveat; k:ClosedWorldAllPresent[] and
k:ClosedWorldAnyPresent[] conservatively extend k:MeasureAllPresent[] and
k:MeasureAnyPresent[] the same way, for CQL's AllTrue and AnyTrue. An instance's is-a to its generic is a
different claim, the same idea at another kind, and is not a construct relation. The
concept-set checks run over the reasoner conformance kit. The finite check runs in the
set's own integration test: CQL's specified tables for `and`, `or`, `not`, `implies`,
and `xor`, reproduced row for row from the three literals' bounds, which is what admits
those five keywords by identity.

== Field Constraints

Where the Semantic Field Model chapter's Constraining Fields section introduces the
constraint apparatus — two patterns, one per parameter shape, both attaching to the
pattern whose field they constrain — this chapter describes how the starter set
supports constraints in practice: what authoring one looks like, how several
constraints on one field compose, how each shape derives its legal set, and how
constraints and default values cohere.

A constraint is first-class content of the pattern it constrains. Unlike a default
value — which needs the Defaults and templates module as its category boundary (see
the Default Values chapter) — a constraint needs no machinery at all: no special
module, no exclusion from any read path, no dedicated accessor. Each constraint
semantic attaches to the constrained pattern as its referenced component, and reading
a pattern's constraints is retrieval by enumeration: walk the semantics attached to
the pattern that are of the two constraint patterns. Identity is declared
descriptively, so the ledger reads as prose — the STAMP author constraint below is
declared as "Taxonomy Field Constraint: STAMP pattern Author field kind-of Author",
the rule's own name saying exactly what it asserts.

Constraint semantics compose conjunctively. Each semantic is one conjunct, and a value
is legal only when every conjunct on its field holds — no override, no precedence, no
disjunction to reason about. A field may carry constraints of both shapes at once, a
taxonomy constraint and a value-set constraint intersecting: legal then means inside
the taxonomy region *and* matching an enumerated member.

The pattern axis is the parameter shape: one constraint pattern per parameter tuple,
never one per datatype, and never a union carried by sentinel values. A kind or
relation field earns its place as a genuine parameter only when every field of the
tuple stays meaningful for every one of its values — the four taxonomy kinds share one
identical (field, kind, anchor) tuple, so one pattern carries all four; value-set
membership carries a different tuple entirely, so it is a pattern of its own — a
shape, never a fifth kind. Every field of every constraint semantic is meaningful: no
k:BlankConcept[] sentinel anywhere in this story.

=== The Apparatus Constrains Itself

The apparatus's own discriminator fields are exactly the closed one-level value lists
the immediate-child kind exists for, and the set constrains them accordingly — as
ordinary content, through the same pattern any other constraint uses:

* "Taxonomy Field Constraint: Taxonomy Field Constraint Pattern Constraint kind field
  immediate-child of Taxonomy field constraint kind" — constrained field =
  k:ConstraintKind[], kind = k:ImmediateChildFieldConstraint[], anchor =
  k:TaxonomyFieldConstraintKind[]: the kind field of every taxonomy constraint holds
  one of the four kinds, and nothing else.
* "Taxonomy Field Constraint: Value-set Field Constraint Pattern Member match relation
  field immediate-child of Member match relation" — constrained field =
  k:MemberMatchRelation[], kind = k:ImmediateChildFieldConstraint[], anchor =
  k:MemberMatchRelation[] again: the relation field of every value-set constraint
  holds an admitted relation, and nothing else — the same concept serving as the
  field's meaning and the constraint's anchor without conflict, the two roles read
  from different fields entirely.

Nothing marks these two semantics as special: they are taxonomy constraints like the
STAMP pattern's four, retrieved the same way, composed the same way. Growing either
closed list is authoring: mint the child concept, and the existing constraint admits
it without being touched — for a relation, the bijection gate additionally requires
its evaluator to ship in the same change.

=== Constraints and Defaults

Constraints and defaults meet at one coherence rule: a default value must satisfy its
field's constraints — a fresh semantic pre-populated from defaults should be legal
where a curator has finished choosing, and loudly illegal where they have not.

k:PreferredReviewerPattern[] shows the finished side: its authored default,
k:Gretel[], is the roster's own first entry, so the default satisfies the value-set
constraint on the very field it fills — a real, constraint-satisfying value, visible
as the _default_ row of <<koncept-pattern-table-PreferredReviewerPattern>> (the
Default Values chapter walks the full round trip).

The loud defaults show the unfinished side, deliberately. k:UninitializedComponent[]
belongs to no domain taxonomy region and no curated value set, and `NaN` matches
nothing under k:EqualMatchRelation[], itself included. So wherever a constrained field
still carries its loud default, constraint checking fails it until someone chooses a
real value — the same machinery that validates finished data announces unfinished
data, the loud-defaults principle of the Default Values chapter restated from the
checking side.

=== Loud Defaults for Every Data Type

What value should a default actually carry? The governing principle is *loud defaults*:
a default must work as an initial value while reading as obviously needing revision —
never Java's silent zero-values, which disappear into real data instead of announcing
themselves. The starter set demonstrates the principle at full breadth with one
pattern carrying a loud default for every data type a pattern field can declare.

koncept-narrative::DataTypeDefaultsPattern[]

<<koncept-pattern-table-DataTypeDefaultsPattern>> shows the pattern's full shape; the
indented _default_ row under each field is read live from the pattern's own default
value semantic, through the same computed identity any editor would resolve.

koncept-pattern-table::DataTypeDefaultsPattern[]

The sixteen decided defaults group into a small number of strategies:

* *The UNINITIALIZED string forms.* String is the literal `UNINITIALIZED`; ByteArray is
  the UTF-8 bytes of `UNINITIALIZED` — the loud String default carried in byte form;
  Array is an array of exactly one element, the String `UNINITIALIZED` — present and
  non-empty, since an empty array would be a silent zero-value.
* *The loud placeholder component.* Component and Concept default to
  k:UninitializedComponent[], the base set's own loud placeholder for a value still
  owed — deliberately not k:BlankConcept[]: Blank means a deliberate not-applicable, a
  quiet, legitimate state, while Uninitialized means a value still owed. ComponentIdSet
  and ComponentIdList are the singleton set and list holding k:UninitializedComponent[]
  — present and non-empty, their one member itself the loud placeholder.
* *Native non-values.* Types whose value space offers a true non-value use it — a
  non-value is louder still, because it cannot be mistaken for data at all. Float is
  `NaN`, which also propagates through arithmetic, so any computation over an unrevised
  default stays loudly not-a-number; Instant is the premundane instant, the time type's
  own before-all-recorded-time marker, chosen over a sentinel date because a true
  non-value cannot be mistaken for a real timestamp.
* *Stretched-sevens sentinels.* Numeric types without a native non-value use a planted
  repdigit: Integer is `777777777` (nine sevens), Long is `777777777777777777`
  (eighteen sevens), and Decimal is `777777777.777` — nine sevens, a decimal point,
  three more sevens, the decimal point placed deliberately to demonstrate the type's
  distinguishing property: a scaled decimal, not an integer. A repdigit signature reads
  as deliberately planted and cannot plausibly occur as natural data, where `MIN_VALUE`
  would read as an overflow bug.
* *Structural values that prove their type.* DiGraph is a deliberate simple cycle — two
  vertices, both k:UninitializedComponent[], with edges in both directions: a cycle can
  never be a tree, so the value proves the field truly holds a graph and not a tree.
  DiTree is the smallest well-formed tree — a single vertex, the loud placeholder at
  its root.
* *A real, resolvable semantic.* The Semantic field's default is the fully qualified
  name description semantic of k:UninitializedComponent[] — a real, resolvable semantic
  whose subject is itself the loud placeholder, so the reference is valid yet plainly
  unrevised.
* *The flagged compromise.* Boolean is `false`: a two-valued type has no loud member,
  so no Boolean default can announce itself as unrevised; `false` is offered as the
  initial value with that limitation stated rather than hidden.
